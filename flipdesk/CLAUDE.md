# FlipDesk

Движок для перепродажи б/у техники в Болгарии. Ищет лоты ниже рынка, считает
справедливую цену и срок продажи, собирает сигналы спроса и выдаёт решение
«брать / не брать» с обоснованием. Покупает и продаёт человек, не система.

**Стек:** Python 3.12 · uv · SQLite · httpx · Playwright · pydantic v2 ·
APScheduler · aiogram (Telegram) · FastAPI + HTMX (дашборд) · Anthropic SDK.

---

## 1. Что система делает

Один цикл, четыре шага:

```
INGEST      площадки → сырые объявления
NORMALIZE   сырое → канонический товар (модель, спек, состояние, дефекты)
VALUE       ценовая полоса + срок продажи + стоимость ремонта + сигналы спроса
DECIDE      score → книга CORE или EDGE → карточка решения в Telegram
```

Потом человек едет и покупает. После продажи факт возвращается в базу и
перекалибрует модель.

Ключевой принцип: **система не оптимизирует прибыль на сделке. Она оптимизирует
прибыль на единицу капитала в единицу времени.** Лот с маржой 60%, который висит
два месяца, хуже лота с маржой 25%, который уходит за неделю. Всё скоринг
строится вокруг этого.

## 2. Две книги

Капитал делится на два портфеля с разными правилами. Это не «стратегия
поосторожнее и стратегия порискованнее» — это разные критерии отбора.

### CORE — 70–75% капитала

Консервативная база. Задача — не заработать много, а не потерять и не встать.

| Параметр | Порог |
|---|---|
| ROI на вложенное | ≥ 25% |
| Медианный срок продажи | ≤ 10 дней |
| Уверенность оценки | ≥ 0,70 |
| Компарабл в выборке | ≥ 8 за последние 45 дней |
| Разброс цен по компарабл | коэф. вариации ≤ 0,20 |

Товары: массовые модели с плотным рынком. iPhone предыдущих поколений, MacBook
Air, ходовые GPU, iPad. То, где цена известна с точностью до 5% и покупатель
находится всегда.

### EDGE — 25–30% капитала, цель +45%

Здесь и только здесь берётся риск. Условие входа жёстче, а не мягче.

| Параметр | Порог |
|---|---|
| ROI на вложенное | ≥ 45% |
| Активный катализатор спроса от `pulse` | обязателен, минимум 1 |
| Медианный срок продажи | ≤ 21 день |
| Одновременных EDGE-позиций | ≤ 2 |
| Доля одной позиции от общего капитала | ≤ 15% |

**+45% берутся не из наценки, а из сегмента.** Накинуть 45% на рыночную цену
нельзя — покупатель за 30 секунд листает конкурентов. Наценка живёт там, где
сравнить не с чем:

- товар оценён рынком по одной функции, а куплен под другую (GPU с большим VRAM
  продаётся по игровым бенчмаркам, покупается под локальный инференс);
- конфигурация редкая, компарабл почти нет (Mac с 64GB RAM, 4TB SSD);
- снято с производства, а спрос под конкретную задачу остался;
- собранный и проверенный комплект против суммы разрозненных частей;
- окно катализатора: релиз новой модели, сезон, регуляторный дедлайн.

**Обязательный стоп-лосс.** У каждой EDGE-позиции с момента выставления работает
лестница снижения. Не «подумаю ещё недельку», а расписание в базе:

```
день 0   ask = target
день 7   −7%
день 14  −12%
день 21  выход по лучшему предложению или перевод в CORE-цену
```

Если позиция дошла до дня 21 — это данные для `calibrator`, а не повод держать
дальше. Зависший лот в EDGE стоит дороже, чем убыток на нём.

## 3. Скоринг

```python
net       = p50_sell − ask − repair_cost − fees − logistics
roi       = net / (ask + repair_cost)
velocity  = 1 / max(days_to_sell_p50, 1)
score     = roi × velocity_norm × confidence × demand_multiplier
```

- `p50_sell` — медиана ценовой полосы из `appraiser`, не оптимистичный максимум.
- `days_to_sell_p50` — медиана времени жизни компарабл-объявлений до снятия.
- `confidence ∈ [0,1]` — функция от количества компарабл, разброса и свежести.
  Мало данных → низкая уверенность → лот не проходит в CORE, даже с высокой маржой.
- `demand_multiplier ∈ [0.7, 1.4]` — от `pulse`. Только он может поднять лот в EDGE.

Никогда не подставляй в `p50_sell` цену активного объявления конкурента. Активная
цена — это хотелка продавца. Считать надо по снятым объявлениям и по факту своих
прошлых сделок.

## 4. Субагенты

Каждый живёт в `.claude/agents/`. Роли не пересекаются, у каждого свой набор
инструментов и своя таблица в базе. Больше агентов ≠ лучше: если у нового агента
нет отдельного источника данных и отдельного выхода — это не агент, а функция.

| Агент | Задача | Пишет в |
|---|---|---|
| `scout` | сбор объявлений с площадок, дедуп, первичный фильтр | `listings_raw` |
| `appraiser` | ценовая полоса, срок продажи, уверенность | `valuations` |
| `teardown` | стоимость и выполнимость ремонта, доступность запчастей | `repair_estimates` |
| `pulse` | спрос, тренды, релизы, новости, сезонность → множитель | `demand_signals` |
| `risk` | краденое, activation lock, юр. и налоговые пороги | `risk_flags` |
| `copywriter` | текст объявления, фотоплан, план ответов | `listing_drafts` |
| `ledger` | P&L, распределение капитала, лимиты позиций | `positions`, `cashflow` |
| `calibrator` | сверка прогноз/факт, подстройка весов скоринга | `model_params` |

Правила делегирования:

- `scout`, `pulse`, `risk` — только чтение сети, никаких записей в код.
- `ledger` и `calibrator` не ходят в сеть вообще, работают по базе.
- Запускай `scout` и `pulse` параллельно в фоне, они независимы.
- `appraiser` не стартует, пока `scout` не закрыл нормализацию: без канонической
  модели ценовая полоса считается по мусору.
- Каждый агент возвращает в главную сессию только итог, не сырые данные. Сырое —
  в базу.

## 5. Схема данных

Минимально необходимое. Не расширяй без причины.

```sql
listings_raw(id, source, source_id, url, title, body, price, currency,
             city, posted_at, seller_hash, images_json, fetched_at)

products(id, brand, model, variant, storage_gb, ram_gb, year, notes)

listings(id, raw_id, product_id, condition, defects_json, completeness,
         ask_eur, is_active, delisted_at)

comparables(id, product_id, condition, sold_price_eur, days_live,
            observed_at, source)

valuations(id, listing_id, p25, p50, p75, days_to_sell_p50,
           confidence, comps_n, computed_at)

repair_estimates(id, listing_id, parts_eur, hours, feasibility, notes)

demand_signals(id, product_id, kind, strength, window_start, window_end,
               source_url, summary)

risk_flags(id, listing_id, kind, severity, detail)

decisions(id, listing_id, book, score, verdict, rationale, decided_at)

positions(id, listing_id, book, bought_eur, repair_eur, listed_at, ask_eur,
          sold_eur, sold_at, days_held, status)

model_params(key, value, updated_at)
```

`seller_hash` — соль + хеш контакта. Сырые контакты продавцов в базу не пишем.

## 6. Конверсия объявления

Задача — чтобы человек купил быстро и без торга. Достигается доказательствами, а
не давлением. В маленьком городе репутация — актив дороже маржи с одной сделки.

Что реально двигает конверсию:

1. **Первое фото — устройство включено, с рабочим столом.** Не коробка, не логотип.
2. **Заголовок по формуле** `Модель + память + цвет + один факт о состоянии + город`.
   Пример: `MacBook Air M1 8/256 Space Gray, батарея 94%, Бургас`.
3. **Блок доказательств в теле:** здоровье батареи в цифрах, скрин «Об этом Mac»,
   серийник пробит при покупателе, чек на замененную запчасть, гарантия 3 месяца
   от себя.
4. **Все известные дефекты — в тексте**, до встречи. Скрытый дефект стоит дороже:
   покупатель находит его на встрече и выбивает скидку больше его цены.
5. **Время публикации** — вечерний пик, 19:00–22:00 по местному.
6. **SLA ответа** — 15 минут в первые два часа. Это самый сильный фактор после цены.
7. **Цена с зазором 5–8%** под торг, круглая. Не «€699», в BG-рынке это читается
   как розница.

Запрещено (жёстко, `copywriter` это знает):
- выдуманная срочность и несуществующие другие покупатели;
- умолчание о дефекте, который известен;
- завышенное состояние («как новый» при следах);
- накрутка отзывов и фейковые аккаунты;
- давление на встрече.

## 7. Правила капитала

Живут в `ledger`, проверяются перед каждым решением. Нарушение — блокирующая
ошибка, а не предупреждение.

- Кэш-резерв ≥ 20% капитала всегда. Не в лотах.
- Одна позиция ≤ 25% капитала (CORE), ≤ 15% (EDGE).
- Открытых позиций ≤ 3, пока капитал < €2000.
- EDGE не финансируется, пока CORE не закрыл минимум 2 цикла в плюс.
- Убыток по позиции фиксируется в день выхода, а не «когда продам нормально».
- При обороте > €5000/мес — стоп на новые лоты до регистрации деятельности.

## 8. Режимы работы

```
paper    решения пишутся в decisions, покупок нет. Обязательные первые 30 дней.
live     карточки уходят в Telegram, покупает человек.
```

Из `paper` в `live` переходим только когда на 20+ решениях медианная ошибка
`p50_sell` относительно факта укладывается в ±12%. Раньше — нет. Модель, не
проверенная на своих данных, оценивает рынок из тренировочных данных, а не Бургас.

Система никогда не совершает покупку или продажу автоматически. Максимум —
карточка решения с кнопкой.

## 9. Границы и законность

- Соблюдай ToS площадок. Уважай `robots.txt`, ставь задержки, не обходи антибот.
  Где есть официальный API или RSS — используй его, а не Playwright.
- Персональные данные продавцов не храним: только хеш контакта и срок сделки.
- `risk` обязан отработать до карточки решения. Серийник, activation lock,
  происхождение, отсутствие чека при цене сильно ниже рынка — всё это флаги.
- Налоговый порог отслеживается автоматически, не по памяти человека.

## 10. Команды

```bash
uv sync
uv run flipdesk init-db
uv run flipdesk scan            # один проход ingest → decide
uv run flipdesk scan --watch    # по расписанию
uv run flipdesk book            # состояние портфеля и P&L
uv run flipdesk backtest        # прогноз против факта

uv run flipdesk web             # дашборд на localhost:8000

uv run pytest
uv run ruff check . && uv run ruff format .
uv run mypy src
```

## 11. Конвенции

- Все деньги — целые центы в `int`, поле с суффиксом `_eur` хранит евро как
  `Decimal`. Никаких `float` в денежных расчётах.
- Любое внешнее значение проходит через pydantic-модель на границе.
- Адаптеры площадок реализуют один протокол `Source` в `sources/base.py`.
  Новая площадка = новый файл, ничего больше трогать не надо.
- Никаких сетевых запросов в тестах. Фикстуры — сохранённые HTML-снапшоты в
  `tests/fixtures/`.
- Каждый модуль имеет тест на граничный случай «данных мало». Это самый частый
  реальный сценарий и самый частый источник уверенной чуши.
- Коммиты в настоящем времени, по-английски, без эмодзи.

## 12. Definition of done

Задача закрыта, когда:

1. Есть тест, который падал до фикса.
2. `ruff` и `mypy` чистые.
3. Если задача трогает скоринг или оценку — прогнан `backtest`, и в PR приложены
   цифры до/после.
4. Если задача добавляет источник данных — добавлен снапшот в фикстуры и
   зафиксирована политика запросов (частота, задержка, User-Agent).
5. CLAUDE.md обновлён, если изменились пороги, книги или правила капитала.

## 13. Порядок сборки

Не строй всё сразу. Каждый этап должен работать на реальных данных до перехода к
следующему.

1. `db` + `sources/olx.py` + нормализация одной категории (iPhone). Ничего больше.
2. `appraiser` на одной категории. Проверить руками на 20 объявлениях.
3. `ledger` + режим `paper`. Месяц решений без денег.
4. `teardown`, `risk`.
5. Telegram-карточки, переход в `live`.
6. `pulse` и книга EDGE. Только после того, как CORE отработал два цикла.
7. `copywriter`, дашборд, `calibrator`.

Пункт 6 — последний по содержанию, а не по важности. EDGE без откалиброванного
CORE это не риск на +45%, это ставка вслепую.
