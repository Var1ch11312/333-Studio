MoSCoW Method
M
Must Have
Критичні вимоги. Без них продукт не працює. Входять до MVP без обговорення. Якщо хоч одна відсутня — MVP провалюється.
S
Should Have
Важливі, але MVP може запустити без них. Додаються одразу після стабілізації MVP (v1.1). Тимчасово замінюються ручними процесами.
C
Could Have
Цінні для product growth але з низьким впливом якщо відкласти. Плануються на v2.0 після підтвердження product-market fit.
W
Won't Have
Явно виключено з поточного релізу. Або операційні задачі (не розробка), або залежать від Could Have, або технічно передчасні.

MVP Визначення мінімального продукту

✅ Що входить в MVP (Must Have)

✓Каталог букетів — список з EUR/BGN цінами та тегами
✓Checkout 5 кроків — адреса + дата + оплата Stripe
✓Stripe оплата — PCI-DSS compliant, webhook + idempotency
✓WhatsApp флористу — деталі + кнопки Accept/Reject
✓5-хв таймаут — автопереключення на наступний Hub
✓Broadcast кур'єрам — first-wins атомарний dispatch
✓Admin Dashboard — Realtime перегляд + ескалація
✓PIN аутентифікація — /admin/* та /hub/* захищено
✓Cron ескалація — перевірка SLA кожні 2 хвилини
✓Інфраструктура — DB схема, міграції, CI, middleware

❌ Що НЕ входить в MVP

✗AI Finder — клієнт обирає вручну з каталогу (→ v1.1)
✗Фото доставки — адмін закриває замовлення вручну (→ v1.1)
✗Admin CRUD каталогу — редагування через Supabase Dashboard (→ v1.1)
✗PWA / офлайн — замовлення через браузер (→ v1.1)
✗Іменинники — маркетинг, не блокує core flow (→ v1.1)
✗AI Агенти — бухгалтер / юрист / маркетолог (→ v2.0)
✗Hub Dashboard — флорист управляє через WA (→ v1.1)
✗E2E Playwright — ручний smoke test достатній (→ v2.0)
✗Figma дизайн — виконується до спринтів (Pre-dev фаза)
✗GTM / Onboarding — операційна задача після деплою
